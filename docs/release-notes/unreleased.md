# Unreleased

Changes merged to `main` that are not yet part of a tagged release. Each
tagged release has its own page in this directory; this page carries what has
landed since the newest one.

Cutting a version empties this page: every entry the tag ships moves onto that
version's page in the release PR itself. `tests/unit/test_unreleased_notes_rotation.py`
holds the page to that — an entry naming an issue or PR a tagged release page
already documents fails the build. An entry that cites released work as context
rather than as its own attribution is exempted by hand there, with the reason.

## Security

- Journal verification no longer presents a self-consistent prefix as proof of
  the complete journal (#3651). Tolerant `load_events` reads now return both
  accepted rows and the 0-based physical indices of discarded non-blank lines;
  blank lines remain valid separators. `JournalVerifyResult` replaces the
  ambiguous `ok` bit with separate chain-consistency, reader-coverage, and
  sealed-identity verdicts. A clean prefix without an external head is
  `unverifiable`; against a seal, deleting the last one or two complete rows is
  a mismatch. Context verification consumes existing intent journal seals when
  present, while artifact and suspension outputs explicitly state when no
  whole-journal seal exists. Checkpoint selection fails closed on any observed
  reader discard without changing the tolerant default for ordinary readers.

- The two Slack webhook receivers (`POST /webhooks/slack/commands`,
  `POST /webhooks/slack/events`) now require a signing secret, matching the
  GitHub receiver. **Behaviour change:** with `SLACK_SIGNING_SECRET` unset
  (and no `slack_signing_secret=` passed to `create_app`), both routes answer
  `404` and create no task; previously they processed the request without
  checking a signature. A configured deployment is unaffected - a correctly
  signed delivery still returns `200` and a wrongly signed one still returns
  `401`. Set the secret before pointing Slack at the endpoint, since the
  `url_verification` handshake is a signed delivery like any other. See
  [`docs/operations/slack-webhooks.md`](../operations/slack-webhooks.md).
- `POST /webhooks/slack/events` validates the payload's shape before reading
  it. The body must be a JSON object, and a present `event` member must be one
  too; a list, string, number, boolean, or `null` in either position now
  returns the documented `400` instead of a `500`. A payload with no `event`
  member is still acknowledged with `200`.
- Paths built from caller-supplied strings are now asserted to stay under
  their base directory. One shared helper,
  `bernstein.core.security.path_containment.contained_subpath`, joins a
  project-relative candidate onto a base and returns it only when
  `realpath` keeps the result inside the resolved base; it is the
  multi-component counterpart to the existing `contained_path`, which takes
  single opaque identifiers. It is used in the fast-path `rename_symbol`
  executor (each `owned_files` entry) and in the `/complete` auto-commit
  hook (the `.sdd/worktrees/<session id>` working directory). A refused
  entry is skipped and logged, matching how each of those functions already
  handles an entry it cannot use, so one bad row does not end a run.
- **Behaviour change:** the same rule is applied at the input boundary, so a
  bad row does not reach a sink in the first place. `POST /tasks` and
  `POST /tasks/self-create` now answer `422` when an `owned_files` entry is
  absolute, carries a `..` component, or contains a NUL byte;
  ordinary project-relative paths such as `src/parser.py` are unaffected.
  The claim boundaries (`POST /tasks/{id}/claim`, `GET /tasks/next/{role}`,
  `POST /tasks/claim-batch`) answer `422` when `claimed_by_session` is not a
  single opaque identifier (`[A-Za-z0-9_.-]+`), which is the shape the
  orchestrator already generates. Both layers are kept: the validator stops
  new bad rows, the helper protects the sink from rows that already exist or
  arrive by another route.
## Added

- MCP server registration from a plugin's `mcp.json` (#3773). The Agent Plugins v1.0.0 `mcpServers` mapping is now parsed into `MCPServerConfig` objects (reusing `parse_server_configs`) and routed through `validate_mcp_configs` before first use; stdio entries expand `${PLUGIN_ROOT}` and `${PLUGIN_DATA}` in commands, args, and env values, with `PLUGIN_DATA` persisted under `~/.bernstein/plugins-data/<plugin-name>/` so a plugin update that re-extracts the source tree keeps the same data directory. An invalid entry (missing or wrong `type`, empty stdio command list) is skipped with a `logger.warning` naming the server and never blocks the rest of the plugin's `mcp.json` from registering. Public surface: `parse_plugin_mcp_manifest(plugin_root)` for callers that only want configs, and `parse_plugin_mcp_manifest_with_diagnostics(...)` for tests and operator tooling that also want the skip reasons. Slice 2 of 2 of #3540 (skill installation from the same plugin ships separately). Refs #3773.
- Muse Code adapter (`muse`, #3538). Wraps the CLI's documented headless mode - `muse --model <id> --disable-approval exec "<prompt>"` - so a Muse Code run gets the same worktree isolation, journaling, and receipts as every other adapter-managed worker; the vendor's own sandbox stays on (the adapter deliberately never passes `--yolo`). Auth is `META_API_KEY` through the filtered worker env. Model routing is strict for the single-model vendor lineup: `muse-spark-1.2` is the default, explicit `muse-*` ids pass through, and a foreign logical name fails loudly at spawn instead of silently remapping. Contract pinned in `tests/contract/contracts/muse.yaml`; docs: `docs/adapters/muse.md`.

- `bernstein readme-l10n` gate for translated READMEs (#3425). `README.<ietf-tag>.md` files mirror the English `README.md` section for section; each translated section carries an HTML-comment binding (`<!-- l10n: en="..." hash="sha256:..." -->`) to a content hash of the English section it mirrors (normalised so prettier/editor noise does not trip the gate). `bernstein readme-l10n verify` recomputes the bindings and exits non-zero on drift, naming the language and the exact stale section heading; it also fails on a translated code block (commands, flags, paths and `bernstein` subcommands must stay verbatim) and on any modification of the verbatim header/footer (logo, badges, language links line, license line). `bernstein readme-l10n sync` rewrites the binding hashes after an English edit; a translated section without a binding is reported, never invented. The language set lives in `[tool.bernstein.readme-l10n] languages` in `pyproject.toml`, so adding a language is a data change, not a code change. The gate runs in the Repo hygiene CI job next to `agents-md verify`. First payload: `README.zh-Hans.md` and `README.zh-TW.md`. Docs: `docs/playbooks/readme-l10n.md`. Refs #3425.
- Clean-run attestation: eval scores now ship with an offline-verifiable proof that the task's ground-truth was never fetched during the run (#2930). Isolation was assumed clean, never proven clean — a contaminated run and an honest run produced identical scorecards. `bernstein.eval.clean_run` seals a signed `CleanRunAttestation` per scored run, following the receipt-is-the-proof pattern of the eval gate (#2520): the task's ground-truth (id, title, completion signals, expected test commands, reference-solution contents) is committed as a `ContrabandSet` of keyed HMAC digests under the operator audit key, so the attestation binds to the answer without ever carrying it and publishing it cannot leak the solution; the task's own golden-source material is derived automatically (`derive_task_reference_blobs`) so a caller cannot silently omit it, coverage counts are sealed into the commitment (a reference-free task seals `reference_source_count == 0` visibly), and declared-but-unloadable reference content refuses to seal (`CleanRunCommitmentError`). The scope boundary comes from the substrate, not from config — the task's worktree root plus the `NetworkPolicy` endpoint allowlist — and without a bounded worktree root the builder **refuses to sign** (`CleanRunBoundaryError`), because a `CLEAN` claim over an unbounded read universe would be vacuous. The scanned activity set is the run's Merkle-chained `EventJournal` rows; the attestation records that head, so an omitted or mutated contaminating access breaks the anchor rather than silently trimming the set — and it binds the journal head only, because the audit-chain mirror carries the attestation's own hash and so cannot sit inside the sealed bytes; the mirror is verified separately by `bernstein audit verify` and by the receipt projection's coverage check. The deterministic scan is a pure membership pass over sealed digests — verdict `CLEAN` iff zero contraband matches and zero out-of-scope accesses, with findings recorded as `(journal index, match class)` positions, never plaintext — and the canonical binding is anchored in the dedicated `eval-clean-run` lineage-spine run and mirrored into the HMAC audit chain as `eval.clean_run_attestation` (hashes and the verdict only), so a single-byte tamper fails `bernstein audit verify` like any tampered chain entry. Verification re-derives, never trusts: `bernstein eval clean-run verify <hash>` recomputes the attestation hash, re-derives the verdict from the embedded activity digests and contraband commitment (a stored `CLEAN` whose embedded evidence contains a match is rejected even when its hashes are internally consistent), rejects an activity set that does not chain to the recorded journal head as *unanchored* (a missing journal fails closed the same way), re-derives the sealed activity set from the anchored rows, and re-checks the spine anchor; `project_clean_run_receipt` projects the mirrored range through the existing COSE / in-toto / transparency audit-receipt envelopes (same KMS adapter, no new key material), checkable by a verifier holding neither the plaintext ground-truth nor the HMAC key. Harness wiring: `TaskEvalResult` carries the attestation and a `DIRTY` verdict zeroes the multiplicative `Safety` factor exactly like a test regression; when no attestation is requested, scoring is byte-for-byte unchanged. Deterministic by construction: identical fixtures and an injected clock seal byte-identical binding bytes and spine anchors. Docs: `docs/sdd/clean-run-attestation.md`, `docs/eval/golden-harness.md`. Refs #2930.
- Multi-tier verifier ladder with signed per-tier receipts (#2927). The pre-merge gate's single boolean becomes a re-derivable coverage claim: when `run_janitor()` is handed a `VerifierLadderContext`, every verifier tier that actually executed for a task — the deterministic completion-signal tier (including attribution and guardrail rows) and, when declared, the LLM judge tier — seals a frozen `TierRecord` (`config_hash` / `inputs_hash` / `evidence_hash` / `verdict`) into the lineage spine under the dedicated `verifier-ladder` run id, kept apart from per-task journals exactly as `eval-gate` is, and mirrors its identity into the HMAC audit chain as a `verifier.tier` event — hashes and the verdict only, never raw diff, rubric, or model output. The composite `LadderReceipt` binds the ordered tier records to a `merge_eligible` claim derived by the pure, fail-closed `derive_ladder_verdict()` — an empty record set, an absent required rung, or any non-`pass` verdict (a `fail` *or* a `skip`) blocks eligibility — and the receipt hash is returned on `JanitorResult.ladder_receipt_hash`. A judge tier that was consulted but never adjudicated (prerequisite signals failed, the LLM call failed, the response was unparseable, an upstream circuit breaker tripped) records verdict `skip` rather than silently vanishing, so degraded coverage is a chain read, not a proof-archive autopsy. Verification re-derives, never trusts: new `bernstein verify ladder <receipt-hash>` re-hashes the stored body, re-runs the verdict derivation over the stored tier records (a forged `merge_eligible` is rejected even when the receipt's hashes are internally consistent), and re-checks every tier's `spine_entry_hash` against the spine entry's content hash, so a substituted or dangling tier record fails by name and a removed or tampered spine fails closed rather than passing trivially. Deterministic by construction: identical tier evidence and an injected clock seal byte-identical canonical payloads, pinned by a committed golden fixture. Additive and default off — without the context the janitor seals nothing and every existing `JanitorResult` consumer sees unchanged behaviour. Docs: `docs/sdd/verifier-ladder.md`, `docs/reference/cli/verify.md`. Refs #2927.
- Artifact contracts are declarable from operator surfaces (#3110). A task's `artifact_spec` (kind `report` / `dataset` / `action_log` / `ops_result`, a workdir-relative `output_path`, optional typed `criteria`) is now a first-class field on a plan step, a backlog entry's YAML frontmatter, the task CLI (`--artifact-kind` / `--artifact-output` / `--artifact-criterion` on `add-task`), and the `POST /tasks` body - all parsed by one shared strict parser, so the surfaces cannot drift and the declared contract survives the wire into the stored task and back on every task response. Fail-closed: a malformed declaration (unknown kind, missing or workdir-escaping output path, unknown key, malformed criterion) is refused at load with the offending field named - it never silently becomes a `code_diff` task completing on a git SHA, which was the previous behaviour of the lenient deserialiser. A declared artifact task completes through the existing artifact path on a signed lineage receipt with no commit, deterministically (same declaration, two fresh `.sdd` dirs, byte-identical canonical bytes and equal `content_hash` / `entry_hash`). The `computer_use` adapter family is the first `output_mode=artifact` row in the strategy matrix, and `task_output_mode` maps a task's declared contract onto that axis so the commit check never fires for a declared artifact task on any adapter. Undeclared tasks are byte-for-byte unchanged. Docs: `docs/operations/artifacts.md`, `docs/reference/capabilities.md`.
- Bernstein-native tool-call evidence provider (#2931). Enforced dispatch can now append an intent-bound `toolcall.attestation` and its referencing `toolcall.enforced_dispatch` marker to the HMAC audit chain before connector I/O becomes reachable. The pair is serialized in one chain transaction, stores argument digests rather than raw arguments, and returns no authorizing handle after a partial append. The optional identity path freezes a lineage public key at spawn, domain-separates and signs the exact pre-dispatch intent, chain position, journal head, monotonic call index, and injected attestation time, while offline verdicts reject substitution and duplicate dispatch. The implementation remains vendor-neutral and preserves the legacy HMAC-only path. Docs: `docs/sdd/toolcall-attestation-interlock.md`.
- Run-attestation receipts (#2931, #3469). `build_run_attestation_receipt` verifies the complete source audit chain, selects a contiguous range by authenticated chain position from the run's unique identity anchor through an explicit HMAC or verified snapshot head, retains interleaved events, and projects the range through the existing deterministic COSE, DSSE/in-toto, and transparency formats. Identity-bound dispatch evidence and universal closure are re-derived from the embedded range. Foreground, multi-cell, detached, and capsule-governed paths emit one idempotent HMAC-chained `run.closure` marker with `completed`, `failed`, `cancelled`, or `abandoned` outcome and an exact run-journal or work-ledger head/count anchor. Clean shutdown seals the journal before closure; the watchdog or next startup may infer `abandoned` only after positive owner-process death and a verified journal-start binding. Absence stays open, duplicate/conflicting markers fail closed, and a later same-run event invalidates the earlier terminal claim. An identity receipt upgrades to whole-run `complete` only from a still-valid run-journal closure, never from a work-ledger marker or serialized verdict. Closure reuses the existing audit key and standard receipt vocabulary. Docs: `docs/sdd/run-attestation-receipt.md`, `docs/sdd/run-closure.md`, `docs/security/audit-receipt.md`.
- Receipt-gated adapter admission (#2610). Adapter resolution moves from name-based to proof-based: `get_adapter` accepts an `AdmissionGate` that the spawn dispatch path supplies, and an adapter resolves only when it can present a sealed admission receipt whose deterministic replay fingerprint still matches the installed binary and the pinned contract. The fingerprint is a projection of `(contract bytes, binary version, golden-transcript replay output)`, so two operators on the same binary version derive byte-identical bytes and a binary that moved under a still-valid receipt is caught as a named divergence rather than riding a stale attestation. The negative path is first class: a skipped, stale, or failing adapter seals a refusal receipt carrying the adapter key, binary path, probe hash, contract hash, conformance run id, refusal reason, the capabilities allowed and forbidden (a refusal forbids `spawn` itself), the admission TTL, and the operator-visible remediation - so a `conformance == "skip"` verdict can no longer read as silent permission. Admissions and refusals alike are mirrored into the HMAC audit chain as `adapter.admission_receipt` events, and `anchor_admission_receipt_in_lineage` seals a receipt as a signed lineage entry through the shared `seal_write` primitive. New `bernstein adapters verify <name>` re-derives the fingerprint locally, fails closed on a mismatch, and `--seal` writes and anchors a fresh receipt. Policy is warn-by-default (`BERNSTEIN_ADAPTER_ADMISSION_POLICY=enforce` makes a refusal a hard stop, `=off` disables the gate); `mock` and `generic` are always exempt so offline work is never blocked. Golden transcripts added for `droid`, `kimi` and `opencode`, and `droid`, `kimi` and `pydantic_ai` joined the nightly conformance canary matrix so a broken upstream release is caught by the matrix rather than mid-run. Docs: `docs/adapters/admission-receipts.md`.
- Browser activity worker: forensically replayable site checks and UI flows on the typed activity boundary (#2523). `bernstein.core.orchestration.browser_worker.BrowserWorker` runs a site check or UI flow as a first-class activity, handed across the same `dispatch_activity` typed boundary any modality's result crosses and anchored into the run journal and HMAC audit chain as any `ActivityKind.BROWSER` result (automatic dispatch by the deterministic scheduler is separate substrate work; the `bernstein activity browser run` command drives the worker and crosses the boundary today). Around every action the worker content-addresses the exact pre-action screenshot and DOM bytes it saw, plus the action receipt, into the run `ContentStore`, and folds them into a per-step anchor `sha256(prev_anchor, sha256(screenshot_bytes + dom_digest), action)`, so the flow report is a single-parent Merkle chain whose head is the run identity and whose observation hashes are the result's `evidence_set_hash`. Every value the worker writes is a pure function of the flow definition and the observed bytes (no wall clock, no counter, no network ordering), so re-running a flow over the same recorded observations reproduces a byte-identical action sequence, report, and verdict; altering one stored observation or one action receipt breaks that step's anchor and every anchor after it, so verification fails naming the exact step index. Check verdicts are recomputed rather than trusted: `verify_browser_flow_report` reattaches the DOM bytes by hash and re-evaluates each assertion offline, so a report whose hashes all recompute but whose recorded verdict disagrees with the anchored bytes fails naming the check id. Only the digest of a typed value ever enters the chain, so a form-filling flow never anchors a secret. Isolation is structural: each run gets a profile directory keyed on the dispatch coordinates `sha256(run_id, stage_id, flow_id)[:16]`, so two concurrent tasks driving the same flow stay disjoint, torn down on every exit path including driver failure. The worker fronts a `BrowserDriver` protocol (`navigate` / `act` / `screenshot` / `dom_snapshot`) with a recorded-tape driver for offline replay and an optional `browser-use` driver installed on demand (the `browser` extra is declared empty, so the backend is not vendored into the lock); a missing backend is a typed `BrowserDriverUnavailable` naming the pip package to install, and driver faults, timeouts, and budget overruns map onto the closed `TerminalState` set (`driver_error` / `driver_timeout` / `driver_unavailable`), never free text. New CLI: `bernstein activity browser run --flow <doc> [--recording <tape>]` submits a flow, `bernstein activity browser verify <run>` replays it offline with per-step and per-check detail, and `bernstein activity verify` now surfaces the browser verdict. Docs: `docs/orchestration/browser-activity.md`.
- `bernstein run --sandbox docker` now provisions a real `DockerSandboxBackend` `SandboxSession` (via `WorkspaceManifest`/`GitRepoEntry`) and attaches it to `AgentSpawner`, so agents actually execute inside the Docker container through the existing `_spawn_via_sandbox_session` path instead of silently falling back to the legacy bind-mount container isolation. `DockerSandboxBackend.create()` bind-mounts the host repo read-only at `/host-repo` and clones it into the container's `/workspace` so agent commits never touch host git state. Backward compatible: without `--sandbox docker` nothing changes, and any provisioning failure (missing `docker` daemon/SDK) logs a warning and falls back to the previous behaviour.

Requires a seed file; combining it with an inline goal or `--plan-file` is a usage error.

JSON hosts merge into their canonical `mcpServers` map (or `context_servers` for Zed); Aider records the entry in its YAML config under `mcp-servers` for community-wrapper consumption (#1676).

## Changed

- Artifact-mode tasks are routed off the git-only run substrate (#2996). A task declaring a non-`code_diff` `artifact_spec` completes on a signed lineage receipt, never a commit, yet its session still paid for the full git machinery: worktree allocation did not branch on the resolved output mode, so every artifact task got a `git worktree add`, a checkout, and an `agent/<session>` branch it never wrote through - held for the task's lifetime and torn down unused, a real disk and setup-time cost on a fan-out of report or dataset tasks, and a muddied isolation story in `spawner_core`. Worktree allocation now branches on the batch's resolved output mode, with the decision in exactly one place - `needs_git_worktree()` in `core/tasks/artifact_completion.py`, next to the `is_artifact_mode()` resolver the completion path already dispatches on - so allocation and completion read the same answer and cannot drift. The branch is scoped to worktree-enabled runs on purpose: disabling worktrees remains the operator's explicit choice to execute in the checkout and applies to artifact and coding tasks alike, so with worktrees off an artifact task spawns in the shared workdir exactly as a `code_diff` task does. Under the default isolation, an artifact-only batch gets an isolated plain directory under `.sdd/workspaces/<session_id>` instead: no checkout, no agent branch, no warm-pool slot (warm slots are pre-provisioned worktrees), and the merge-back and salvage paths are structural no-ops for it because the session is never registered in the worktree maps. The workspace is removed at reap and by the dead-agent cleanup entry point, removed by a leak guard when any exception escapes the spawn after allocation (a security-floor, admission, or sampling-params refusal included), and orphans are swept alongside orphan worktrees. A batch containing any `code_diff` task keeps the existing warm-pool/worktree flow unchanged, and an undeclared task still defaults to `code_diff` - pure coding runs are byte-for-byte unaffected, and the existing worktree isolation tests pass unmodified. The second git-only assumption is closed at its door: the provider-batch path (`batch_api`) commits by construction - its prompt requests a unified diff and its completion path applies, stages, and commits it - so `try_submit` now refuses an artifact-mode task up front, before eligibility checks, routing, worktree creation, or any provider call, with the refusal naming the supported path (the realtime spawn's artifact completion path, which the dispatch loop takes in the same tick); previously such a task submitted straight through and could only have ended in a git-shaped completion its declared contract forbids. Teaching `batch_api` the artifact completion path was deliberately not done - it would duplicate the artifact pipeline behind a second entry point for a route nothing takes. The no-worktree property is pinned by tests that inspect what was actually allocated rather than only the task result: `WorktreeManager.create` never called, no `.sdd/worktrees/<session>` entry, no `agent/<session>` branch, spawn cwd is the plain workspace; and the batch refusal test proves an otherwise fully batch-eligible artifact task produces no provider submission, no job record, no worktree, and no session claim. Docs: `docs/operations/artifacts.md`, `docs/operations/activity-boundary.md`, `docs/reference/capabilities.md`. Refs #2996.
- `bernstein telemetry verify-span` now uses the same exit-code convention `trace verify-projection` has shipped and documented since v3.9.0, so one script drives both verification commands: `0` = verified, `1` = input could not be evaluated (missing journal, malformed span JSON, unreadable input, or a run never anchored into the audit chain), `2` = verification failed. The command's shipped contract was only `0` genuine / hard nonzero rejection, so subdividing the nonzero space keeps every caller that treats nonzero as "not verified" working. **Behaviour change:** a forged span -- an id that does not recompute from its journal entry, or an anchor that does not match the chain -- now exits `2` instead of `1`; an unverifiable input stays nonzero but becomes `1` exclusively. A rejection is still a hard error, never a warning, and `trace verify-projection` is unchanged. The `otel.projection` rows the command consumes are now read through the chain's verifying query rather than an unvalidated scan, so an audit chain that fails its own HMAC verification makes the span unverifiable (exit `1`, with the integrity failure named on stderr) instead of lending its rows as evidence -- previously a tampered chain row could still corroborate a span. A cross-command test pins both commands' behaviour and documented contracts to the one table so a future drift in either fails a named test. The docs also now state what `verify-span` does not prove: it binds a span to a journal entry and a chain anchor, and does not vouch for the journal's own authorship or the semantic truth of the span's attributes. Docs: `docs/observability/otlp-export.md`. Refs #3256.
- `bernstein audit export --standard` no longer accepts `dora` or `finos-aigf`; the click choice list is `ai-act` only. The previous control maps for those two standards contained only placeholder rows (`status: "todo"`, `selector: "TODO"`) and have been removed from `SUPPORTED_STANDARDS` until their clause mappings are reviewed by subject-matter experts. Operators who pass either value now receive a clean usage error rather than a TODO-only zip (#1316).
- Documentation names the command `--audit` belongs to. The flag is declared on `bernstein run`, but the README and `docs/index.md` introduced it beside the `bernstein -g "<goal>"` form they teach, where `bernstein --audit -g "..."` exits with `No such option '--audit'`. The prose now leads with `BERNSTEIN_AUDIT=1`, which works on every form, and qualifies the flag as `bernstein run --audit` where it is mentioned. Also in `docs/use-cases.md`.
- The README named `src/bernstein/adapters/use_cases.py` as the single source of truth for the 48 wired-in adapters `bernstein integrations list` enumerates. That file holds 47 keys - it carries the end-user copy, while the registry in `src/bernstein/adapters/registry.py` decides what resolves - so a reader checking the count against the file the README named came up one short. The README now names the registry as the enumeration source and the copy file as what it is.
- `bernstein consensus` and `bernstein issue-to-pr` now print a deprecation warning on invocation (#3144). Both groups inspect state no shipped runtime writes: nothing outside `consensus_relay.py` calls `RelayStore.append`, and the only importers of `bernstein.core.orchestration.issue_to_pr` are `main.py` and the CLI module itself, so on any real project every subcommand reports an empty result. They stay registered through the 3.10 line with the warning on stderr (stdout stays machine-parseable) and are unregistered in 4.0.0. The core modules stay importable and unchanged; the issue is cancelled outright if the missing producer ships first. Docs: `docs/reference/cli-reference.md`, `docs/orchestration/issue-to-pr.md`. New `tests/unit/test_cli_deprecation_notices.py`.
- `quickstart`, `init-wizard`, `validate` and `routine` fold into the commands that already own their domain (#3140): `bernstein demo --flask-todo`, `bernstein init --wizard`, `bernstein plan validate` and `bernstein schedule routine <sub>`. All four top-level names stay registered as deprecated aliases for the whole 3.x line, printing a notice on stderr (stdout stays machine-parseable) and forwarding to the new location; they are unregistered in 4.0.0. No capability moves without its flags: `demo` gains `--keep` so the scenario's temp directory can still be preserved, and `init` gains `--non-interactive` so the wizard's unattended path survives the flag conversion. Three contracts of the receiving command are enforced on the folded path rather than inherited from the folded one - `demo` is mock-by-default, so `demo --flask-todo` runs on mock agents and only resolves an installed CLI behind `--real` (forwarding an unresolved adapter would have made a bare `demo --flask-todo` spawn billable agents that plain `demo` never spawns); `--dry-run` promises no agents are spawned, and the scenario has no preview mode, so the combination is refused instead of running a live orchestration; and an unset `--timeout` takes the scenario's own 300s budget rather than `demo`'s 120s. `init --wizard` refuses `--add-badge` and `--remote` for the same reason: the wizard never reaches that code, so accepting them would drop them silently. The `i` shortcut keeps landing on the interactive setup it has always opened - an alias value may now carry flags, so `i` expands to `init --wizard` rather than becoming plain `init`. `bernstein --help` lists `demo --flask-todo` in place of the duplicate `quickstart` entry, and the first-run hint printed by `init` names the new spelling. Docs: `docs/reference/cli-reference.md`, `docs/getting-started/quickstart-demo.md`, `docs/architecture/plans.md`, `docs/routine-scenarios.md`, `docs/operations/commands.md`, `docs/operations/deployment-guide.md`. New `tests/unit/test_fold_subcommands.py` asserts each fold against the target callback rather than against help text: the forwarding is the whole content of the change and a `--help` assertion does not see it.
- `bernstein changelog` and `bernstein run-changelog` swap names in one release (#3142). The orchestration-specific command (agent-produced diffs, the one a bernstein user reaches for after a run) now holds the bare name `bernstein changelog`, and the conventional-commit generator moves under `bernstein changelog conventional`. - `bernstein benchmark` is a deprecated alias for `bernstein eval` (#3143). The two groups overlapped on `run` and `swe-bench`. `programbench`, `compare`, `simulate` and `receipt` had no `eval` counterpart, so they are served under `bernstein eval programbench`, `bernstein eval compare`, `bernstein eval simulate` and `bernstein eval receipt` rather than dropped: the alias is removed in v4.0.0, so a subcommand without an `eval` destination would be a capability deleted rather than a spelling retired. ## Fixed

- A run journal whose trailing bytes are an incomplete multi-byte character no
  longer wedges the tolerant reader (#3971). `load_events` treated undecodable
  bytes as an error from the codec rather than as a malformed line, so one
  class of crash produced two outcomes depending on where in the byte stream it
  stopped: a discarded physical line index when the write stopped between two
  characters, and a bare `UnicodeDecodeError` — carrying no line index, and
  losing every earlier event in the file — when it stopped inside one. Bytes
  that are not valid UTF-8 now travel the same two reader policies as
  unparsable JSON: discarded by the tolerant reader and reported in
  `discarded_line_indices`, raised by `strict=True` as a `JournalParseError`
  naming the 0-based physical line. Physical line indices are unchanged for
  every journal that read successfully before. A row whose only defect is one
  undecodable byte is discarded rather than repaired, so no silently altered
  event can enter the chain.
- The CLI reference no longer names command spellings that do not resolve. It
  claimed `bernstein commit-stats`, `bernstein incident`, and `bernstein
  postmortem` were live deprecated aliases after v4.0.0 removed them, and
  listed `bernstein task compose`, `task sync`, `task notes`, and `task parts`
  as invocable when those commands are registered at the top level (or, for
  `notes`, nowhere). `bernstein report commits --help` printed the removed

- `ClusterServiceImpl.RegisterNode` no longer raises `TypeError` on every
  gRPC node registration. The handler called `NodeRegistry.register()` with
  `NodeInfo`'s own constructor keywords (`name=`, `url=`, `capacity=`,
  `labels=`, `cell_ids=`), but `register()` takes one positional `NodeInfo`;

- `load_plan` no longer lets an out-of-range enum value escape as a bare `ValueError`. `_parse_step` built `Scope(...)` and `Complexity(...)` directly from the step dict, so a plan carrying `complexity: epic` crashed with an unhandled traceback out of a function whose documented failure contract is `PlanLoadError` -- and every caller catches `PlanLoadError` alone. Both enum conversions now go through a guard that raises `PlanLoadError` naming the step, the stage, the field, the offending value, and the accepted values, and `load_plan`'s `Raises:` section states the contract. `bernstein plan validate` already reported enum violations through its schema pre-check; the loader now honours the same contract for every other path that loads a plan without that pass (#3515).
- `plan_schema.validate_plan` now enforces the types and ranges `PLAN_JSON_SCHEMA` declares, instead of reporting valid for plans the schema rejects. A non-string enum value (`role: 7`, `model: false`) is a type error rather than a silently skipped check, array items in `files`, `constraints`, `context_files` and stage `depends_on` must be strings (`files: [42]` no longer passes), `max_agents` honours the schema's `minimum: 1`, and a non-string top-level `name` is rejected. Booleans no longer satisfy integer checks (Python's `bool` subclasses `int`, JSON Schema's `integer` excludes it), so `max_agents: true` stops passing the minimum check and a boolean `priority` or `estimated_minutes` is a type error rather than an accepted value. Keys the schema does not declare (`additionalProperties: false`) are reported as *warnings* through a new optional `warnings` accumulator on `validate_plan` -- plans carrying extra keys keep validating for now, and `bernstein plan validate` prints them as warnings with exit 0; the error-level enforcement is deferred to the next major release. The command also keeps the schema's role *type* verdict as an error while still demoting the role *membership* verdict to a warning, since operators extend roles under `templates/roles/` but a non-string role is not a custom role. The validator's docstring no longer claims equivalence to the schema and lists the remaining gaps (#3516).
- `load_parked_sessions()` no longer conflates "genuinely zero parked sessions" with "the parked-session store was never written this run". It now returns a `ParkedSessions` result carrying an `available` flag alongside the session ids, true only when the `.sdd/runtime/spawn_supervisor/parked.json` marker or a `respawn_exhausted` failure-log entry was actually found. `SupervisorSnapshot.parked_available` threads that flag through `aggregator_snapshot`, so `bernstein status`, `bernstein supervisor status` and `bernstein fleet`'s summary line and JSON output say `parked state unavailable` instead of silently reading as `0 stuck` when the supervisor never wrote anything this run (#3453, step 1 of the issue: the spawner still does not call `SpawnSupervisor.spawn()`, so this makes the store's silence honest without wiring it yet).
- The eval-gate verdict receipt store no longer follows a symlinked `.sdd/eval/gate`. `verdict_receipt_path` compared `os.path.realpath(base)` against `os.path.realpath(candidate)` for containment but returned the *unresolved* candidate, so when the gate directory (or `.sdd`, or `.sdd/eval`) was itself a symlink to an outside directory, both sides of the `commonpath` check resolved into the symlink's target, the check passed vacuously, and `read_verdict_receipt` followed the link and parsed a same-named receipt JSON from wherever it pointed - the identical hole the verifier-ladder store closed in #3409, and the same posture the MCP shutdown barrier's refusal of a symlinked `.sdd` established (#3080). The path helper now walks each store component and refuses a linked one with a named `ValueError`, and after containment passes it returns the *resolved* candidate, so the subsequent read or write cannot follow a same-named symlink planted inside the store; the `sha256:` hash-format validation and the containment check are unchanged. The component probe uses `is_filesystem_link` rather than `Path.is_symlink()`, because `is_symlink()` answers `False` for an NTFS junction and a junctioned store component would bypass a symlink-only check on Windows - and the ladder store's own walk from #3409 had exactly that gap, so `ladder_receipt_path` moves onto the same helper in the same change. The refusal degrades exactly as an absent receipt does: `read_verdict_receipt` returns `None`, `verify_verdict_receipt` reports `no verdict receipt for <hash>`, and `bernstein eval gate-verify` exits `1` with that named failure and no traceback. A normal, non-symlinked store is byte-for-byte unchanged - build/verify round-trip, determinism, and golden-fixture tests pass as-is. The regression tests pin the attack layouts by name: a genuine receipt sealed elsewhere, planted in an outside directory that a victim's symlinked gate store points at, must produce no parsed content and a named refusal, at the module surface and through the CLI - and a junction-simulating store component must be refused identically on both stores. Refs #3410.
- Declared task context now reaches the worker. Three surfaces parsed `context_files` and all three dropped the declaration before a worker saw anything: the backlog parser read it into `ParsedBacklogTask` but `to_task_payload()` omitted it from the POST /tasks payload; `load_plan()` parsed and schema-validated `PlanConfig.context_files` but every caller (`run_bootstrap`, `run_confirm`, `dry_run_cmd`) binds the config half of the return value to a discard; and the spawner's read of `task.metadata["context_files"]` - which lists the files in the worker's task-specific CLAUDE.md - consulted a key nothing in `src/` ever wrote. A fourth drop point surfaced while verifying the wire end to end: `_post_task_to_server` builds the POST body field-by-field and never forwarded metadata, so even a stamped declaration died at the server boundary. The fix connects the wire at each break rather than adding a parallel channel: `to_task_payload()` carries the declaration under the payload's `metadata["context_files"]` mapping, which the task store already persists verbatim (`ticket_type` and `affected_paths`, which fall out at the same spot, ride in the same mapping; frontmatter `depends_on` names ticket ids and needs resolution, so it is deliberately not forwarded); `load_plan()` stamps plan-level `context_files` onto every produced task's metadata at parse time, fixing the discarding callers at the source; and the planner POST forwards that one metadata key. The attachment is recorded, not just copied: at dispatch each declared path is resolved in declared order against the worktree the worker actually reads from and content-addressed as `(path, order, sha256)`; an unresolvable path keeps its position in the record with a reason code (`missing`, `is_directory`, `unreadable`, `outside_root`, or `invalid` for a declaration the filesystem cannot represent, such as an embedded NUL byte - normalization errors are caught per entry, so a malformed declaration is a recorded absence, never a spawn abort) and a log warning instead of being silently skipped, and does not abort the spawn. Crash-recovery resumes go through the same flow: `spawn_for_resume` previously bypassed the attachment recording entirely, so a resumed task silently lost its declared context from the run record; both spawn paths now share one helper, resolution runs against the preserved worktree so the record pins the bytes as they exist after the crashed agent's edits, and the resumed session emits the same `context.files_attached` event (resume does not rewrite the preserved worktree's CLAUDE.md, which still carries the context section the original spawn wrote). The resolved set is stamped on the `AgentSession` and recorded in the run journal as a `context.files_attached` event next to `agent_spawned` - the mechanism the spawn path already uses for per-session run state - so which reference material a worker saw, at which content, is answerable offline; `verify_context_attachments` in the new `core/agents/context_attachments.py` recomputes every digest from the bytes for the round-trip check. The entry shape matches what #3366 defines for its read-side context manifest (ordered entries, `sha256:` digests, reason-coded absences), so that work can adopt these records instead of minting a second shape. Tickets and plans that declare nothing produce byte-identical payloads, worker context, and journal streams; a test asserts each. New `tests/unit/test_context_files_attachment.py` drives the real backlog parser and plan loader through the payload into the real spawner-side context-writing path against a tmp worktree, with each recorded-set property pinned by a test named for it. Refs #3375.
- `bernstein doctor` no longer reports a red `Secrets` row on a workspace `bernstein init` has just created, and no longer prints two rows for the same provider. Two checks answered for the same `secrets:` block. `_doctor_check_secrets` reads the block out of YAML (trying `.sdd/config.yaml`, then `bernstein.yaml`) and probes through `check_provider_connectivity`; it works and is kept. `_doctor_check_secrets_yaml` re-read only `bernstein.yaml`, through `parse_seed`, and called `check_secrets_connectivity`, a name defined nowhere in the tree, inside a broad `except Exception` -- and neither of its outcomes was correct. `parse_seed` enforces the whole seed contract including a non-empty `goal`, but the seed `init` writes leaves `goal:` commented out with an instruction to fill it in, so `init` followed by `doctor` -- the first two commands a new operator runs -- reported `configuration error: Seed file must contain a non-empty 'goal' string` against a correctly set-up workspace, on a row about secrets, with the unrelated remedy `Check bernstein.yaml syntax`. With a `secrets:` block actually configured, the undefined name raised `ImportError` and the same clause reported `configuration error: cannot import name 'check_secrets_connectivity'` with the same misdirected remedy, while the working check printed a real verdict one row above -- the duplicate row is why a check that had never produced a correct answer went unnoticed. - The next-steps hint printed by `bernstein init` no longer points at `examples/quickstart/`. `examples/` is a repository directory and is not part of the wheel, so an operator who followed the documented `pipx install bernstein` / `pip install bernstein` path had no such directory to open - the hint named the one artefact the install they had just performed does not ship. - The `CI gate` required check could be satisfied by the synthetic stub on a diff that carries code. `ci-gate-stub.yml` publishes a `CI gate` success for pull requests whose diff is entirely inside `ci.yml`'s `paths-ignore` list, which would otherwise wait forever for a context that never runs. `paths` and `paths-ignore` filters are evaluated per file with OR semantics, so a mixed diff (some paths ignored, some not) fires both workflows and both published the same context name; the stub completed in seconds while the real test matrix was still queued, branch protection read a completed success, and a pull request merged to `main` with no test run against its code (#3016). No `on:` filter can express "every changed file is ignored", so the stub now derives the verdict in-job: a `classify` job evaluates the pull request's changed paths against `ci.yml`'s own `on.pull_request.paths-ignore` list (read from the file rather than duplicated, so the two cannot drift apart) and the emitting job takes its check-run name from the result - `CI gate` only when every changed path is ignored, `CI gate stub (not applicable)` otherwise. Branch protection keys on the check-run name, so under the second name the stub is structurally unable to satisfy the requirement and `ci.yml` is the only emitter for any diff carrying code; fully paths-ignored pull requests keep merging exactly as before. An `if:` skip is not usable here, because GitHub counts a skipped required check as passing and posts the unresolved `name:` template when a job is skipped. - The run preflight banner and the plan/approval box no longer quote a fixed Anthropic/`sonnet` per-task rate for a model the run does not resolve. Both surfaces derived the estimate from `_model_cost` / `_MODEL_COST_USD_PER_1K`, which returns a non-zero fallback rate (`0.005`/1k) for any model missing from the blended table, while the run's actual `total_cost` is metered by `price_model_usage` against `MODEL_COSTS_PER_1M_TOKENS`, which reports an explicit `$0` for the same unrecognized model - so a `:free` route whose real `total_cost` was `$0.000000` was shown a phantom `~$0.25-$0.75 per task` and labelled `sonnet`. The free/zero decision now flows through one shared predicate, `bernstein.core.cost.model_prices.is_free_route`, which consults the *same* pricing table the metering path uses: a model id ending in `:free`, or any model `price_model_usage` prices at `$0`, is estimated at `$0` / "free route - no cost" and labelled with the resolved model id. The preflight estimate keys on the resolved model rather than the adapter name alone, and the plan estimator falls back to the seed's global `model:`/`cli:` when a seed sets no `role_model_policy`, so the plan labels the resolved model instead of `sonnet`. - The install-identity HTTP Message Signature on Browser Rendering requests now binds the POST body. `browser_rendering.py` signed only the `@method` and `@target-uri` derived components and handed the payload to httpx via `json=`, so the signature attested nothing about the body - an intermediary could rewrite the JSON request without invalidating the signature the receiving endpoint uses to attest which install issued the call. The bridge now serializes the body exactly once, folds an RFC 9530 `Content-Digest` over those exact bytes into the RFC 9421 covered-component set, and sends the same bytes via `content=` so the signature covers the payload; a body swap now fails verification at the receiver. New helper `bernstein.core.identity.http_signing.content_digest` computes the header. Verification of already-signed requests is unchanged (#2640).
- `DelegationLedger.record_hop` no longer forks the HMAC delegation chain under concurrent writers. The tail read, HMAC computation, and append were not serialized, so two threads - or two processes (task server, spawner, CLI) extending the same run - could recover the same `prev_hmac`/`hop_index` and each append a record embedding that stale linkage, forking the chain and breaking `verify_run_chain` for the whole run. The read-modify-write is now held under a per-run in-process `threading.Lock` keyed by `run_id` plus an OS `flock(LOCK_EX)` on a per-run lock file, mirroring the audit chain's cross-process append lock; it degrades to the in-process lock alone on platforms without `fcntl`. The receipt format and chaining construction are unchanged, so existing receipts still verify (#2640).

- AI-BOM adapter entries are no longer collapsed by binary: `AdapterEntry` records `binary`, but the dedupe key was `(name, version, sha256)` only, so two adapters sharing a name/version/hash but resolved from different binaries merged into one entry, and *which* binary survived depended on the order the snapshot listed them in. The emitted BOM therefore stopped being a pure function of the run, and named a binary the run may not have used - a false statement in a document meant for compliance review, and one that reached both the CycloneDX (`bernstein:binary` property) and SPDX (`bernstein:binary` annotation) encodings. `binary` is now part of the adapter identity, so the entries stay distinct and the output is canonical under any input permutation. The ordering key used by `verify_bom` is extended to match, making adapter ordering total so a swap of two otherwise-equal adapter entries is detected as tampering rather than tying.

The orchestrator subprocess gains a `--model` arg (env fallback `BERNSTEIN_MODEL`) threaded from run bootstrap, `AgentSpawner` accepts `default_model`, and `_coerce_model_for_non_claude_adapter` - previously a universal no-op because no adapter defines `default_model` - uses it to replace internal Claude tier names (`opus`/`sonnet`/`haiku`) emitted by the heuristic/bandit selectors and retry escalation, which non-Claude endpoints reject (e.g. MiniMax HTTP 400 `unknown model 'opus'`). Precedence is deny-wins and the posture is fail-closed: a deny-listed command (`rm -rf`, `git push --force`, `DROP TABLE`, `curl ... | bash`, control-plane/credential writes, and the rest of the list) is rejected by the production path regardless of interactive mode, and every decision the gate acts on is appended to the HMAC-chained audit log under `.sdd/audit/` as an `auto_approve_decision` event carrying the matched pattern - so an auditor can replay the chain and prove which calls were rejected or auto-approved and why. - Sandbox relaxation no longer drops the `scope_enforcement` guardrail for backends that expose the whole repository. Relaxation of `scope_enforcement` is now gated on the active backend declaring a task-scoped mount (new `SandboxCapability.SCOPED_MOUNT`, resolved from `BERNSTEIN_SANDBOX_RUNTIME`); a whole-repo mount keeps the boundary enforced (ASK), while a backend that genuinely scopes its mount can still opt in. `file_permissions` relaxation and the non-sandboxed path are unchanged. Reported by Dmitriy Filatov (Malder).
- Intent capsule verification now derives every authoritative value from signed or Merkle-chained state instead of from caller-supplied or unsigned input (#2649). `verify_intent_conformance` took the run to verify from the unsigned on-disk capsule record, so repointing that record's `run_id` at any clean run laundered a drifted run into a clean verdict; the run is now read from the signed `intent.capsule` audit entry, a capsule record naming a different run fails as tampering, and the journal must carry exactly one `intent.capsule_bound` anchor matching the task and capsule hash before conformance is evaluated. `evaluate_conformance` recorded `file_scope_globs`, `permitted_adapters`, and `expiry_ts` without enforcing any of them and treated `allow_unclassified` as a no-op, so a capsule's declared scope constrained nothing beyond its action-class allow-list; all four are now enforced as divergences (`file_scope_violation`, `adapter_not_permitted`, `capsule_expired`, `unclassified_event`), with segment-wise glob matching so `src/*.py` no longer admits `src/nested/deep.py`. `classify_journal_event` resolved a worker-stamped `action_class` ahead of the reviewed tool map, letting a drifting worker relabel its own actions (a `Bash` call stamped `git.commit` classified as a commit); the reviewed map now wins and the stamped label is the fallback for unrecognised tools only. `assemble_intent_drift_escalation` signed whatever capsule and verdict its caller passed, so a caller could mint a signed, spine-anchored receipt attesting drift against a fully conformant run by supplying a fabricated capsule plus a self-consistent verdict; it now resolves the capsule through the same chained authority the verifier uses (it must match the `intent.capsule` entry, the run must be the signed one, and the journal must carry the matching capsule-bound anchor), then recomputes the verdict and signs only that. Capsule expiry is enforced against HMAC-covered audit-chain timestamps rather than the journal's `ts` field, which is excluded from the payload hash and so could be edited in place to erase or manufacture a divergence in a signed verdict. Tool names are normalised before the reviewed map is consulted, so a trailing space no longer lets a worker-stamped label win; common shell aliases are mapped. Every action class an event claims is now checked rather than only the most authoritative one: `tool` and `action_class` are both worker-written, so preferring either alone moved which field was authoritative instead of removing worker control, and a `Read` call honestly stamping `shell.exec` was being silenced by the reviewed map. Only events that claim to be actions can count as `unclassified_event`, so `allow_unclassified: false` no longer flags ordinary structural journal rows. File-scope checking fails closed: a mutating action that records no path while a scope is declared is a `path_unrecorded` divergence. A capsule-governed run now has three distinct verification states. `seal_capsules_bound_to_run`, called by the orchestrator at run completion, commits the journal's head hash and event count to the chain as a new `intent.journal_seal` event; the journal's Merkle chain recomputes from genesis, so every prefix of a valid journal verified cleanly on its own and a worker could delete the trailing rows that convicted it. A **sealed** run is fully attested (truncation and same-length rewrites both detected, the latter by the head hash alone); an **unsealed** run still has its conformance computed and any drift reported, but its completeness is explicitly not attested (exit 4), because withholding drift until a seal exists would let a worker suppress its own drift by never finishing; a **mismatched** seal is tampering. Drift escalation works on in-flight runs and records the seal state it was cut under. Sealing is idempotent: a retry returns the existing entry and writes nothing, since the process writing an attestation can die between the write and the acknowledgement and a duplicate could never be withdrawn from an append-only chain. Capsule expiry is checked against capsule-lifecycle chain entries only (approval, seal, drift): approval entries alone could only ever flag a capsule minted already-expired, while scanning every entry carrying the same `task_id` matched 27 unrelated event types and let one ordinary later entry condemn an honest run permanently. `permitted_adapters` and `file_scope_globs` fail closed on absent input (`adapter_unrecorded`, `path_unrecorded`), since a constraint that applies only when the worker volunteers the field being checked is not a constraint. Absolute paths no longer satisfy workspace-relative globs. `IntentCapsule` normalises its field types on construction, matching the coercion `from_dict` already applied on read: without it a loosely-typed value (a float `expiry_ts`, as an upstream `time.time() + ttl` produces) canonicalised one way in memory and another after a round trip, so verification rejected an honest capsule as tampered. Read-only `bernstein intent verify` minted and wrote audit HMAC key material when none existed, producing a key that cannot authenticate the existing chain and reporting the resulting HMAC failures as tampering; it now loads the key read-only via `load_audit_key` and exits `3` with an explicit missing-key error.
- The spawned-agent prompt path did not enforce the `source_adapter` provenance filter that `SQLiteMemoryStore.query()` and `CrossTaskKB.subscribe()` already supported: `_load_persistent_memory()` read every matching row via `get_relevant()`, which had no adapter filter at all, and injected the content into the prompt verbatim regardless of which adapter wrote it. A row written under one adapter's provenance (or a foreign one) could therefore steer a different adapter's spawned agent. `get_relevant()` now accepts the same `read_only_from_adapters` allow-list as `query()`, and `_load_persistent_memory()` enforces a `MemoryTrustPolicy` (`bernstein.core.memory.trust_policy`) by default: untagged rows (today's operator/CLI writes, and pre-migration data) stay trusted, but a row tagged with an explicit `source_adapter` is only replayed if that adapter is on the policy's allow-list. Configurable via `BERNSTEIN_MEMORY_TRUST_POLICY` / `BERNSTEIN_MEMORY_TRUST_ADAPTERS`; see `docs/operations/memory.md`. Reported by Dmitriy Filatov (Malder).
- Passing a seed config (top-level `goal:` / `model:`, no `stages:`) as the positional plan file argument now raises a clear error naming the seed-vs-plan distinction and pointing at `bernstein.yaml` auto-discovery or `--seed <file>`, instead of the generic `Plan file must contain a 'stages' list` message. A top-level `cli:` key alone does not trigger this, since `cli` is also a valid staged-plan default and is not a reliable seed signal on its own (#3009).
- `bernstein api-check` and `bernstein ab-test` are now registered on the CLI. Both modules shipped complete (`cli/commands/api_check_cmd.py`, `cli/commands/ab_test_cmd.py`), were listed in the lazy-import map, and were documented twice each in `docs/reference/cli-reference.md`; `dep-impact`'s own help text cross-references `api-check`. No `add_command` call ever made either reachable, so following the documented invocation produced `No such command`. The gap was invisible to the suite because every test drove command implementations directly rather than the top-level group. `tests/unit/test_cli_command_registration.py` now walks the CLI reference and resolves every command heading it names through the real `cli` object, so a documented-but-unregistered command fails in CI instead of in a user's terminal (partial implementation of #3139; the `impact` group consolidation in that issue is unaffected and still waits on #3135).
