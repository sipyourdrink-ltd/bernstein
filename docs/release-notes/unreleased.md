# Unreleased

Changes merged to `main` that are not yet part of a tagged release. Each
tagged release has its own page in this directory; this page carries what has
landed since the newest one.

## Security

- `bernstein_stop` now contains the `workdir` it is given. The MCP shutdown
  signal path is resolved and proven to stay inside the named project root,
  and the root must already hold a `.sdd` directory. **Behaviour change:** a
  `workdir` that was previously accepted without containment is now refused,
  including a directory that is not a Bernstein project, a path that traverses
  out of one, and a root whose `.sdd` is a symlink pointing elsewhere. A
  refused call creates no directory and writes no file, and returns the
  structured tool error instead of a `status`. Both the stdio server and the
  remote HTTP transport route through the same barrier. See
  [`docs/mcp/server.md`](../mcp/server.md). Refs #3080.
- `bernstein_stop` screens the `workdir` for shape before it reads the
  filesystem. Resolving a path stats one entry per component, and the remote
  HTTP transport applies no tool schema, so the caller previously chose how
  many components the barrier walked. **Behaviour change:** a `workdir` that
  is not text, or is longer than a path may be on this filesystem, is now
  refused on its byte count with the same structured tool error, before any
  resolve. An input the filesystem cannot represent, such as an embedded NUL,
  is reported as that error too rather than as a raw filesystem message.
  Refs #3080.

## Added

- Receipt-gated adapter admission (#2610). Adapter resolution moves from name-based to proof-based: `get_adapter` accepts an `AdmissionGate` that the spawn dispatch path supplies, and an adapter resolves only when it can present a sealed admission receipt whose deterministic replay fingerprint still matches the installed binary and the pinned contract. The fingerprint is a projection of `(contract bytes, binary version, golden-transcript replay output)`, so two operators on the same binary version derive byte-identical bytes and a binary that moved under a still-valid receipt is caught as a named divergence rather than riding a stale attestation. The negative path is first class: a skipped, stale, or failing adapter seals a refusal receipt carrying the adapter key, binary path, probe hash, contract hash, conformance run id, refusal reason, the capabilities allowed and forbidden (a refusal forbids `spawn` itself), the admission TTL, and the operator-visible remediation - so a `conformance == "skip"` verdict can no longer read as silent permission. Admissions and refusals alike are mirrored into the HMAC audit chain as `adapter.admission_receipt` events, and `anchor_admission_receipt_in_lineage` seals a receipt as a signed lineage entry through the shared `seal_write` primitive. New `bernstein adapters verify <name>` re-derives the fingerprint locally, fails closed on a mismatch, and `--seal` writes and anchors a fresh receipt. Policy is warn-by-default (`BERNSTEIN_ADAPTER_ADMISSION_POLICY=enforce` makes a refusal a hard stop, `=off` disables the gate); `mock` and `generic` are always exempt so offline work is never blocked. Golden transcripts added for `droid`, `kimi` and `opencode`, and `droid`, `kimi` and `pydantic_ai` joined the nightly conformance canary matrix so a broken upstream release is caught by the matrix rather than mid-run. Docs: `docs/adapters/admission-receipts.md`.
- Browser activity worker: forensically replayable site checks and UI flows on the typed activity boundary (#2523). `bernstein.core.orchestration.browser_worker.BrowserWorker` runs a site check or UI flow as a first-class activity, handed across the same `dispatch_activity` typed boundary any modality's result crosses and anchored into the run journal and HMAC audit chain as any `ActivityKind.BROWSER` result (automatic dispatch by the deterministic scheduler is separate substrate work; the `bernstein activity browser run` command drives the worker and crosses the boundary today). Around every action the worker content-addresses the exact pre-action screenshot and DOM bytes it saw, plus the action receipt, into the run `ContentStore`, and folds them into a per-step anchor `sha256(prev_anchor, sha256(screenshot_bytes + dom_digest), action)`, so the flow report is a single-parent Merkle chain whose head is the run identity and whose observation hashes are the result's `evidence_set_hash`. Every value the worker writes is a pure function of the flow definition and the observed bytes (no wall clock, no counter, no network ordering), so re-running a flow over the same recorded observations reproduces a byte-identical action sequence, report, and verdict; altering one stored observation or one action receipt breaks that step's anchor and every anchor after it, so verification fails naming the exact step index. Check verdicts are recomputed rather than trusted: `verify_browser_flow_report` reattaches the DOM bytes by hash and re-evaluates each assertion offline, so a report whose hashes all recompute but whose recorded verdict disagrees with the anchored bytes fails naming the check id. Only the digest of a typed value ever enters the chain, so a form-filling flow never anchors a secret. Isolation is structural: each run gets a profile directory keyed on the dispatch coordinates `sha256(run_id, stage_id, flow_id)[:16]`, so two concurrent tasks driving the same flow stay disjoint, torn down on every exit path including driver failure. The worker fronts a `BrowserDriver` protocol (`navigate` / `act` / `screenshot` / `dom_snapshot`) with a recorded-tape driver for offline replay and an optional `browser-use` driver installed on demand (the `browser` extra is declared empty, so the backend is not vendored into the lock); a missing backend is a typed `BrowserDriverUnavailable` naming the pip package to install, and driver faults, timeouts, and budget overruns map onto the closed `TerminalState` set (`driver_error` / `driver_timeout` / `driver_unavailable`), never free text. New CLI: `bernstein activity browser run --flow <doc> [--recording <tape>]` submits a flow, `bernstein activity browser verify <run>` replays it offline with per-step and per-check detail, and `bernstein activity verify` now surfaces the browser verdict. Docs: `docs/orchestration/browser-activity.md`.
- Cost-aware scheduling: USD budgets, pool accounting, batch and cache policies (#2354). A deterministic cost policy layer under `bernstein.core.cost.scheduling`. USD ceilings per task / run / day are enforced before dispatch against a hash-pinned, config-overridable price table (`cost_policy.pricing`, schema-validated non-negative rates; shipped defaults sourced from the existing leaf pricing table). Each dispatch decision is a pure function of `(price table, spend ledger, caps)` with a deterministic `decision_hash`, so identical ledgers and price tables reproduce byte-identical decisions; a halt seals a receipt naming the policy inputs (`price_table_hash`, `ledger_state_hash`, `policy_hash`) and the projected overrun, anchors the decision bytes in the `cost-dispatch` lineage spine, and mirrors the identity into the HMAC audit chain as `cost.dispatch_receipt`. `bernstein cost policy verify <decision_hash>` recomputes the decision from the stored bytes and re-checks the spine anchor offline (a forged admit / zeroed overrun fails like a tampered chain entry). Usage is attributed to named pools (the ledger `quota_envelope`) with independent caps, and `bernstein cost policy preflight` surfaces pool exhaustion before a run starts rather than mid-run. Batch dispatch and cache-window fan-out (one warm-up call primes a shared prompt prefix for M cache-hitting workers) are gated on declared per-adapter capability maps in `bernstein.adapters._contract` -- refused, never faked, on an adapter without the surface; cache windows default off. `bernstein doctor` flags a stale price table. Config: `cost_policy` (`pricing`, `caps`, `pools`, `cache_window`). Docs: `docs/operations/cost-aware-scheduling.md`.
- `bernstein run --sandbox docker` now provisions a real `DockerSandboxBackend` `SandboxSession` (via `WorkspaceManifest`/`GitRepoEntry`) and attaches it to `AgentSpawner`, so agents actually execute inside the Docker container through the existing `_spawn_via_sandbox_session` path instead of silently falling back to the legacy bind-mount container isolation. `DockerSandboxBackend.create()` bind-mounts the host repo read-only at `/host-repo` and clones it into the container's `/workspace` so agent commits never touch host git state. Backward compatible: without `--sandbox docker` nothing changes, and any provisioning failure (missing `docker` daemon/SDK) logs a warning and falls back to the previous behaviour.
- `bernstein run --worker <role>` (new flag) spawns a single worker agent with the given role directly against the seed goal, bypassing manager decomposition - a supported path for models that cannot drive the manager's task-server workflow. Requires a seed file; combining it with an inline goal or `--plan-file` is a usage error.
- `bernstein skills catalog` command group promotes the MCP catalog browse / list / search / install / upgrade / info / status surface to skill packs. Source variants (github, git, npm, file, directory) resolve through the existing `plugin_installer`; catalog manifests carry an Ed25519 signature that the install verifies against the catalog's `signer_pubkey`. Every install / upgrade appends a `skill.catalog.install` event to the HMAC-chained audit log under `.sdd/audit/` with `(manifest_url, manifest_sha256, manifest_signer_pubkey, install_id, prev_chain_digest)`; reverting and replaying the chain pulls the identical sha and refuses installation if the upstream sha drifted. `skills.lock` is extended with `[[catalog]]` rows and `[[lineage_receipt]]` rows so two parallel worktrees launched from the same chain head observe identical skill versions, and an upgrade in one worktree produces a deterministic adopt/pin decision in the other. The existing lineage-v1 gate (`bernstein.core.lineage.gate.check_skill_lockfile`) rejects PRs whose lockfile references a manifest sha not present in the chain's known-good set. Catalog cache lives under `.sdd/skills_catalog/` with revalidation honouring `BERNSTEIN_SKILLS_CATALOG_TTL` (#1796).
- `bernstein desktop-register --host <name>` covers the remaining priority hosts: Cursor, Continue, Cline, Zed, and Aider, alongside the existing Claude Desktop and Claude Code adapters. JSON hosts merge into their canonical `mcpServers` map (or `context_servers` for Zed); Aider records the entry in its YAML config under `mcp-servers` for community-wrapper consumption (#1676).
- `bernstein doctor --substrate` reports which detected hosts have Bernstein registered, which do not, and which are stale (canonical command/args differ from the recorded entry) (#1676).
- Operator docs at `docs/substrate/{cursor,continue,cline,zed,aider}.md` cover install, verification, and uninstall per host (#1676).
- Slack bidirectional driver with attested approvals: `bernstein chat serve --platform=slack` connects via Socket Mode, dispatches `/bernstein` slash subcommands, decodes Approve/Reject block actions, debounces `chat.update` per channel, signs every outbound message with an Ed25519 detached signature over `(install_id, session_id, content_hash)`, and appends each approval resolution to the HMAC-chained audit log as a `chat.slack.approval` event covering `(approver, message_ts, decision, tool_call_hash, worktree_id)`. Approvals are worktree-pinned: cross-worktree resolutions raise `CrossWorktreeApprovalError` and emit a `chat.slack.approval_rejected` audit entry. Optional `bernstein[slack]` extra pulls in `slack-sdk` (#1794).
- Discord bidirectional driver with attested approvals: `bernstein chat serve --platform=discord` connects via the Discord gateway, dispatches application-command interactions through `on_command`, decodes Approve/Reject component clicks whose `custom_id` encodes `approve:<id>` / `reject:<id>`, debounces per-message edits to one update per second, signs every outbound message with the install's Ed25519 keypair, and appends each approval resolution to the HMAC-chained audit log as a `chat.discord.approval` event covering `(approver, interaction_id, decision, tool_call_hash, worktree_id, partition_id)`. Approvals are pinned both to a worktree and to a channel-scoped scheduling partition: cross-worktree resolutions raise `CrossWorktreeApprovalError`, cross-partition resolutions raise `ChannelPartitionMismatchError`, and either failure emits a `chat.discord.approval_rejected` audit entry. The shared partition helper lives at `bernstein.core.orchestration.scheduler_partitions` (used by both the Slack and Discord drivers). Optional `bernstein[discord]` extra pulls in `discord.py` (#1795).

- `bernstein recipes repair-lineage <name>` resolves a forked recipe definition lineage by naming the branch to follow (`--pick <hmac>`, accepting a 16-char prefix). The definition lineage is append-only, so recovery is additive: the losing branch stays in `recipes history`, the choice is itself a receipt on the chain, and the latest resolution wins. Without `--pick` the competing branches are listed and the command exits `1`, so an unresolved fork is never read as resolved. A forked lineage otherwise fails closed on every operation for that name, with the error pointing at this command. Docs: `docs/operations/recipes.md` (#2673).

## Changed

- `bernstein recipes fire` records a fire only against work a task sink actually accepted, so it now requires a reachable and authenticated task server. A fire whose submission is refused (no server reachable, or an auth rejection such as `401`) writes no receipt and exits `2` instead of the previous exit `0`, so a script cannot read a failed submission as a successful run. A paused recipe still fires nothing and exits `0`; a load or registration error exits `1`. Docs: `docs/operations/recipes.md` (#2673).
- `bernstein audit export --standard` no longer accepts `dora` or `finos-aigf`; the click choice list is `ai-act` only. The previous control maps for those two standards contained only placeholder rows (`status: "todo"`, `selector: "TODO"`) and have been removed from `SUPPORTED_STANDARDS` until their clause mappings are reviewed by subject-matter experts. Operators who pass either value now receive a clean usage error rather than a TODO-only zip (#1316).
- `bernstein_approve` (MCP) is an approval gate rather than an unconditional completion. It reads the task first and acts only on the state the task machine holds a finished result in for sign-off (`bernstein.core.tasks.lifecycle.APPROVABLE_TASK_STATUSES` - `pending_approval`), recording the approver's note as the result summary. Approving a task in any other state is now refused with a structured `task_not_awaiting_approval` error naming the current status, and no state-changing request is sent - previously any task in any state was force-completed with the caller's note as its result summary, so an unfinished task could be marked done with an invented summary. `planned` is refused with a hint naming the plan decision: plan mode records that decision on the plan (`POST /plans/{plan_id}/approve`), and releasing a single task instead would start the work while the plan is still `pending`, after which `POST /plans/{plan_id}/reject` has nothing left to cancel. The sign-off `pending_approval -> done` is now a declared transition, so the one state the verb acts on is no longer rejected by the task server; `pending_approval` is therefore no longer a terminal status. The worker completion path moves to the new `bernstein_complete` tool (`task_id` plus a required `result_summary`, `standard` tier), which posts to `POST /tasks/{id}/complete` from the states a worker holds a task in (`open`, `claimed`, `in_progress`) and refuses `waiting_for_subtasks`, `orphaned`, and `pending_approval` with a structured `task_not_completable` error, so the completion verb cannot finish a parent whose subtasks are still running or a task whose worker is gone; MCP-native workers that used `bernstein_approve` as their completion verb should call `bernstein_complete` instead. Neither gate establishes which worker is calling: a caller holding `tasks:write` can still complete a task another worker is executing, which is bounded by scoping the credential per task rather than by the tool. The streamable HTTP transport carried its own copy of the unconditional completion, so both surfaces now share one gate (`bernstein.mcp.approval_gate`) and connecting over HTTP is no longer a way around it, and the bundled `orchestrate_goal` prompt no longer tells a model to approve a task that looks blocked. Docs: `docs/mcp/server.md` (#3081).
- Mission status projection: a halted phase no longer halts the whole mission and is no longer reported as the active phase (#2683). Phases already run under isolated budget envelopes at dispatch; the projection now matches that isolation by skipping halted (and passed) phases when selecting the active phase and reporting the mission `halted` only when no phase remains runnable, so an exhausted phase envelope no longer masks a runnable sibling. Both the active phase and the overall state are hashed into `mission_status_hash`, so this is a deliberate hash-affecting change: `MISSION_STATUS_SCHEMA_VERSION` is bumped from 1 to 2, and `project_mission` / `project_mission_from_ledger` accept an explicit `schema_version` so an archived ledger reproduces its original v1 status hash byte for byte. Halt semantics stay chain-anchored: a halted phase still seals its halt receipt onto the work ledger and the HMAC audit chain. The mission digest embeds `mission_status_hash`, so its `digest_hash` and `receipt_id` move with the projection. Notes: `docs/release-notes/v3.9.0.md`.
- Documentation names the command `--audit` belongs to. The flag is declared on `bernstein run`, but the README and `docs/index.md` introduced it beside the `bernstein -g "<goal>"` form they teach, where `bernstein --audit -g "..."` exits with `No such option '--audit'`. The prose now leads with `BERNSTEIN_AUDIT=1`, which works on every form, and qualifies the flag as `bernstein run --audit` where it is mentioned. Also in `docs/use-cases.md`.
- The README named `src/bernstein/adapters/use_cases.py` as the single source of truth for the 48 wired-in adapters `bernstein integrations list` enumerates. That file holds 47 keys - it carries the end-user copy, while the registry in `src/bernstein/adapters/registry.py` decides what resolves - so a reader checking the count against the file the README named came up one short. The README now names the registry as the enumeration source and the copy file as what it is.

## Fixed

- `bernstein doctor` no longer reports a red `Secrets` row on a workspace `bernstein init` has just created, and no longer prints two rows for the same provider. Two checks answered for the same `secrets:` block. `_doctor_check_secrets` reads the block out of YAML (trying `.sdd/config.yaml`, then `bernstein.yaml`) and probes through `check_provider_connectivity`; it works and is kept. `_doctor_check_secrets_yaml` re-read only `bernstein.yaml`, through `parse_seed`, and called `check_secrets_connectivity`, a name defined nowhere in the tree, inside a broad `except Exception` -- and neither of its outcomes was correct. `parse_seed` enforces the whole seed contract including a non-empty `goal`, but the seed `init` writes leaves `goal:` commented out with an instruction to fill it in, so `init` followed by `doctor` -- the first two commands a new operator runs -- reported `configuration error: Seed file must contain a non-empty 'goal' string` against a correctly set-up workspace, on a row about secrets, with the unrelated remedy `Check bernstein.yaml syntax`. With a `secrets:` block actually configured, the undefined name raised `ImportError` and the same clause reported `configuration error: cannot import name 'check_secrets_connectivity'` with the same misdirected remedy, while the working check printed a real verdict one row above -- the duplicate row is why a check that had never produced a correct answer went unnoticed. The redundant check and its call site are removed; `_doctor_check_secrets` covers a superset of its inputs, so no case loses coverage. A fresh `init` now reports `Secrets manager | not configured (using env vars)`, and a configured seed reports the provider's real connectivity verdict. New `tests/unit/test_doctor_secrets_single_row.py` (#3349).
- The next-steps hint printed by `bernstein init` no longer points at `examples/quickstart/`. `examples/` is a repository directory and is not part of the wheel, so an operator who followed the documented `pipx install bernstein` / `pip install bernstein` path had no such directory to open - the hint named the one artefact the install they had just performed does not ship. It now points at `bernstein quickstart`, which carries its own inline copy of the sample project and works from any install.
- `--plan-only` no longer executes the run when the plan came from a positional plan file. `plan_file` is a positional argument, so `bernstein run plan.yaml --plan-only` took the `plan_file` dispatch in `_run_impl`, which called `bootstrap_from_goal` and returned before the `plan_only` check further down was ever consulted: a task server, a watchdog, a spawner, a live agent, a worktree, a commit and the merge path, exit code 0, with the flag silently dropped. Reproduced twice in fresh repositories on 3.11.0. The `plan_only` block now runs ahead of the whole `--plan-file` / `--from-plan` dispatch, since the flag is a property of the run rather than of how the plan was supplied. With a plan file present the preview renders the *loaded* plan through the existing `load_plan_from_yaml` -> `create_plan` -> `PlanBuilder` path, so all of the plan's tasks appear with their roles and models instead of a synthetic single-task plan built from the plan's name; `--from-plan --plan-only` and `--plan-only` on an inline goal or seed are unchanged, and `--worker` with a plan file still raises its usage error ahead of the preview. Two consequences of rendering a real plan are fixed with it: the preview tail for the plan-file case now prints `bernstein run <plan_file>` rather than `bernstein run --from-plan <saved.md>`, because `_load_plan_goal` reads only the `**Goal:**` line out of the saved markdown and would re-decompose from the plan name, dropping every task just previewed; and `_save_plan_markdown` writes UTF-8 explicitly, because the render always emits status glyphs and the platform default encoding raised `UnicodeEncodeError` on a cp1252 locale. New `tests/unit/test_issue_3255_plan_only_honors_plan_file.py` patches `bernstein.core.bootstrap.bootstrap_from_goal` (the name `_run_impl` imports inside the function body, so patching the `run_bootstrap` attribute would pass without proving anything) and asserts it is never reached for the goal, plan-file, and `--from-plan` invocations (#3255).
- Two more agent-log consumers now resolve the log across every worktree layout instead of hardcoding the legacy one. `capture_cli_adapter_usage`'s `_resolve_session_log` (`bernstein.core.cost.cli_adapter_usage`) and `AgentLogAggregator._resolve_log_path` (`bernstein.core.agents.agent_log_aggregator`, which feeds `check_stalled_tasks`) each probed only `.sdd/worktrees/<id>/.sdd/{runtime,logs}/<id>.log`, so a session under the current default worktree layout (`.sdd/runtime/worktrees/<id>/`) got no signal at all: usage accounting silently under-reported tokens for the affected run, and stall profiling ran on an empty log summary rather than failing loudly. Both now reuse `_resolve_agent_worktree_dir` (the same helper the reap tick's liveness probe uses, see below) for the worktree-directory lookup instead of reimplementing it. `AgentLogAggregator.parse_log` also gained an explicit `log_path` parameter, and its one caller inside `check_stalled_tasks` now passes `session.log_path` - the remote runtime bridge, container, and sandbox-session spawn paths report their own log at `<spawn_cwd>/.sdd/logs/<id>.log`, which no candidate layout would find; `capture_cli_adapter_usage` already accepted an explicit path and keeps that behaviour. New `tests/unit/test_agent_log_layout_resolution.py` pins all four layouts and the explicit-log-path preference for both consumers (#3216).
- The reap tick's log/`.git` liveness probe now resolves the agent log in every worktree layout instead of one hardcoded path. `_refresh_heartbeat_from_signals` looked only at `<workdir>/.sdd/worktrees/<id>/.sdd/runtime/<id>.log` and that directory's `.git`, which is one of the four layouts this codebase writes agent logs into: the current default worktree layout (`.sdd/runtime/worktrees/<id>/`), the legacy layout, the worktrees-disabled root log, and any spawn path that reports its own `session.log_path` - the remote runtime bridge, container, and sandbox-session paths all log to `<spawn_cwd>/.sdd/logs/<id>.log`. A session outside the legacy layout therefore had no log signal at all. A bridge-backed session felt that worst: it also has `pid=None` and gets no heartbeat protocol JSON, since `bernstein.bridges` never writes one and the single pre-spawn touch is never refreshed, so with all three signals blind it aged out at `heartbeat_timeout_s` however healthy the remote run was. Both paths now go through the shared `_resolve_agent_log_path` / `_resolve_agent_worktree_dir` helpers the sibling probe `_probe_liveness_signals` already used. A session with no per-agent worktree gets no git signal rather than falling back to the root `<workdir>/.git`, which is shared mutable state whose freshness cannot be attributed to one session. The log stays a weak signal in every layout: the `_MAX_LOG_ONLY_HEARTBEAT_TICKS` cap still applies. New `tests/unit/test_heartbeat_signal_layouts.py` (#3215).
- `WALWriter._load_tail` no longer resets the hash chain to `GENESIS_HASH` when the trailing WAL line is torn. A write interrupted by an ungraceful process exit leaves a partial final line; the tail loader fell back to `(count - 1, GENESIS_HASH)`, so the next `append` chained its `prev_hash` off genesis rather than off its real predecessor and the chain forked silently at the truncation point - `verify_chain` then reported a break at the wrong position, or, for consumers that never walk the chain from the run start, missed the fork entirely because the file stayed internally consistent from the fork point onward. The loader now rescans for the last entry whose stored `entry_hash` equals the SHA-256 of its own payload and resumes both `seq` and `prev_hash` from that entry, so a partially-written line can never become the chain anchor. A torn line is not an entry and no longer consumes a sequence number: the append after a torn tail continues at `last_valid_seq + 1` instead of skipping one (#3270).
- `WALWriter.append` no longer produces duplicate `seq` numbers when the durability write fails. The line was written and fsynced before `self._seq` / `self._prev_hash` advanced, so an `fsync` raising `ENOSPC` or `EIO` left the line durably on disk while the in-memory counters stayed put; a caller retrying once the underlying error cleared reused the same `seq`, yielding two WAL lines with identical `seq`, breaking the monotonic-`seq` invariant and leaving the run's hash chain permanently inconsistent. `append` now records the file length before the write and truncates back to it if the write, flush, or fsync raises, then re-raises the original error - on-disk and in-memory state can no longer diverge, and the retry re-appends the same entry with the same `seq` and `prev_hash`. The rollback is best-effort and never masks the original error (#3271).
- Crash recovery no longer trusts WAL entries whose hash chain does not check out. `find_orphaned_claims` and `get_uncommitted_entries` iterated the WAL and treated every parsed entry as authoritative without verifying that `entry_hash` matched the payload or that `prev_hash` linked to the previous entry, so a corrupted WAL - or one that arrived by some path other than the writer - drove force-claims for whatever `task_id` it named; the integrity the WAL format provides was enforced only for callers that explicitly opted into `verify_chain()`, and the crash-restart path did not. New `WALReader.iter_verified_entries` applies the same two checks `verify_chain` makes and drops entries failing either, and both recovery paths read through it. Verification is per entry rather than a whole-file gate: a crashed run's WAL legitimately ends in a torn line, and gating the file would discard the genuine orphans recovery exists to reclaim. The line parsing shared by `iter_entries` and `iter_verified_entries` moves into `_iter_parsed`, which yields the raw record so `entry_hash` is recomputed against the bytes as written (#3272).
- `WALRecovery.close_wal` now fsyncs the WAL directory after writing the `.closed` sidecar marker. The marker file's own contents were fsynced but the parent directory was not, and POSIX only guarantees a new directory entry survives a crash once the directory itself is fsynced - so a crash immediately after recovery could leave the marker invisible on the next boot, `is_wal_closed` reported the WAL as still open, and recovery re-scanned a WAL it had already fully handled, reintroducing the unbounded re-scan the marker exists to prevent and contradicting the crash-survival property the module docstring documents. Failure to open or fsync the directory is logged rather than raised, so closing a WAL still succeeds on filesystems that reject directory fsync (#3273).
- `HeartbeatStatus.phase` no longer borrows the heartbeat file's `status` field. `HeartbeatMonitor.check` computed `phase=heartbeat.phase or heartbeat.status`, and the two fields mean different things: `status` describes the heartbeat file's own lifecycle, `phase` describes the agent's work stage. The pre-spawn writer in `spawner_core` emitted only `{"timestamp": ..., "status": "starting"}`, so every consumer of `phase` received `"starting"` while nothing in the tree assigned that value as a phase - a surface that disagreed with the runtime, which is what led an earlier reading to conclude the Tier-1 watchdog's starting-phase grace window was dead configuration and propose removing it, escalating a starting agent at 200s from `high` to `critical`. Both halves are fixed together: the `or` fallback is gone, so an absent `phase` has one meaning (the writer reported no work stage) and surfaces as the empty string, and the pre-spawn writer now emits `phase="starting"` explicitly. That writer is the only source of the phase for an adapter with `consumes_heartbeat_dir=False`, which never overwrites the spawn-time file, so the grace window keeps applying to that population; a regression test pins the severity at the 200s boundary. Both pre-spawn write sites now share one `_touch_prespawn_heartbeat` helper. New `tests/unit/test_heartbeat_phase_field.py` (#3202).
- The heartbeat escalation ladder and the Tier-1 watchdog no longer let a chattering runner log defer a stalled agent forever. Both consult the runner log's mtime before acting on a stale heartbeat, and every CLI adapter except `claude` merges the child's stderr into that same file via `stderr=subprocess.STDOUT`, so provider retry chatter, a progress spinner, or a runtime deprecation warning refreshed the mtime with no real progress. The check re-applied on every tick and reset the ladder each time, so the deferral had no upper bound: a stalled agent was never escalated and held its worker slot until the wall-clock reaper fired. The deferral is now bounded by `AGENT.liveness_suppression_cap_s` (900s, overridable via `tuning.agent.liveness_suppression_cap_s`). Below the cap a fresh log still defers the kill and still suppresses the incident, so a slow first turn keeps the grace it was given (#3012); past that much continuous heartbeat silence the mtime is treated as output noise and the ladder escalates normally. The cap is asserted to sit above `heartbeat_starting_timeout_s` and below the wall-clock hard cap so a retune cannot silently restore the unbounded behaviour or start reaping agents mid-first-turn. Both halves of the gate are bounded: the kill path in `_escalate_heartbeat` and the incident path in `_check_heartbeat_findings` (#3058).
- A session with no local PID no longer takes down the whole orchestrator tick. `AgentSession.pid` is typed `int | None`, and the remote runtime bridge spawn path sets it to `None` before transitioning the session to `working` - the run executes remotely, so there is no local process to point at. `_refresh_heartbeat_from_signals` passed that value straight into `_is_process_alive` and on to `platform_compat.process_alive`, whose `if pid <= 0` guard raised `TypeError: '<=' not supported between instances of 'NoneType' and 'int'`. Because the tick calls `reap_dead_agents` outside any `try/except` (unlike the `integrate_idle_detection` and `retry_pending_pushes` steps either side of it), the failure was not contained to the one session: every other agent's reap, the pending push retry, and the evolution cycle were skipped along with it. Type checking could not catch it, since `AgentSession` resolves as Unknown inside `agent_lifecycle.py` and every attribute read there is already reported as `reportUnknownMemberType`. The liveness probe is now guarded exactly as `_probe_liveness_signals` already guarded its own call, so a pid-less session falls through to the file signals (heartbeat protocol JSON, agent log, worktree `.git` mtime) and is judged from those; `process_alive` accepts `int | None` and answers `False` for it, matching the answer it already gave for a zero or negative PID, since several callers read a PID out of session state or a runtime JSON file where it is legitimately absent. Such a session is not treated as alive when it has no file signals either, so it still ages out and is reaped on the heartbeat timeout exactly like a local one. New `tests/unit/test_reap_none_pid_session.py` (#3212).
- `_refresh_heartbeat_from_signals` no longer lets a dead agent's own log noise sustain its heartbeat all the way to the 90-minute hard cap. Roughly 35 of the ~40 CLI adapters merge stderr into the agent log via `stderr=subprocess.STDOUT`, so a provider retry loop, a progress spinner, or a deprecation warning kept the log's mtime moving after the process had already exited, and `reap_dead_agents` read that mtime as real liveness with no bound. A heartbeat refreshed only from the plain log (or the worktree `.git` mtime) is now capped at `_MAX_LOG_ONLY_HEARTBEAT_TICKS` (3) consecutive reap ticks before the session is left to age out; a confirmed-live PID or the heartbeat protocol JSON still refresh unconditionally and reset the counter (#3058).
- The `CI gate` required check could be satisfied by the synthetic stub on a diff that carries code. `ci-gate-stub.yml` publishes a `CI gate` success for pull requests whose diff is entirely inside `ci.yml`'s `paths-ignore` list, which would otherwise wait forever for a context that never runs. `paths` and `paths-ignore` filters are evaluated per file with OR semantics, so a mixed diff (some paths ignored, some not) fires both workflows and both published the same context name; the stub completed in seconds while the real test matrix was still queued, branch protection read a completed success, and a pull request merged to `main` with no test run against its code (#3016). No `on:` filter can express "every changed file is ignored", so the stub now derives the verdict in-job: a `classify` job evaluates the pull request's changed paths against `ci.yml`'s own `on.pull_request.paths-ignore` list (read from the file rather than duplicated, so the two cannot drift apart) and the emitting job takes its check-run name from the result - `CI gate` only when every changed path is ignored, `CI gate stub (not applicable)` otherwise. Branch protection keys on the check-run name, so under the second name the stub is structurally unable to satisfy the requirement and `ci.yml` is the only emitter for any diff carrying code; fully paths-ignored pull requests keep merging exactly as before. An `if:` skip is not usable here, because GitHub counts a skipped required check as passing and posts the unresolved `name:` template when a job is skipped. New `scripts/ci_gate_stub_guard.py` and `tests/unit/test_ci_gate_stub_workflow_yaml.py`, which fails if the stub can name its check `CI gate` for any diff containing a non-ignored path. `docs/operations/ci.md` also records the adjacent rerun hazard: rerunning a workflow resets its check-run, so the newest `CI gate` instance on a head SHA can be a stale success from an earlier attempt while the real run is still in flight, and a readiness probe must enumerate every instance on the SHA and require `completed`/`success` rather than reading the latest one.
- The run preflight banner and the plan/approval box no longer quote a fixed Anthropic/`sonnet` per-task rate for a model the run does not resolve. Both surfaces derived the estimate from `_model_cost` / `_MODEL_COST_USD_PER_1K`, which returns a non-zero fallback rate (`0.005`/1k) for any model missing from the blended table, while the run's actual `total_cost` is metered by `price_model_usage` against `MODEL_COSTS_PER_1M_TOKENS`, which reports an explicit `$0` for the same unrecognized model - so a `:free` route whose real `total_cost` was `$0.000000` was shown a phantom `~$0.25-$0.75 per task` and labelled `sonnet`. The free/zero decision now flows through one shared predicate, `bernstein.core.cost.model_prices.is_free_route`, which consults the *same* pricing table the metering path uses: a model id ending in `:free`, or any model `price_model_usage` prices at `$0`, is estimated at `$0` / "free route - no cost" and labelled with the resolved model id. The preflight estimate keys on the resolved model rather than the adapter name alone, and the plan estimator falls back to the seed's global `model:`/`cli:` when a seed sets no `role_model_policy`, so the plan labels the resolved model instead of `sonnet`. The estimate and the final cost are therefore drawn from the same source and agree at `$0` for a free run (#3013).
- The install-identity HTTP Message Signature on Browser Rendering requests now binds the POST body. `browser_rendering.py` signed only the `@method` and `@target-uri` derived components and handed the payload to httpx via `json=`, so the signature attested nothing about the body - an intermediary could rewrite the JSON request without invalidating the signature the receiving endpoint uses to attest which install issued the call. The bridge now serializes the body exactly once, folds an RFC 9530 `Content-Digest` over those exact bytes into the RFC 9421 covered-component set, and sends the same bytes via `content=` so the signature covers the payload; a body swap now fails verification at the receiver. New helper `bernstein.core.identity.http_signing.content_digest` computes the header. Verification of already-signed requests is unchanged (#2640).
- `DelegationLedger.record_hop` no longer forks the HMAC delegation chain under concurrent writers. The tail read, HMAC computation, and append were not serialized, so two threads - or two processes (task server, spawner, CLI) extending the same run - could recover the same `prev_hmac`/`hop_index` and each append a record embedding that stale linkage, forking the chain and breaking `verify_run_chain` for the whole run. The read-modify-write is now held under a per-run in-process `threading.Lock` keyed by `run_id` plus an OS `flock(LOCK_EX)` on a per-run lock file, mirroring the audit chain's cross-process append lock; it degrades to the in-process lock alone on platforms without `fcntl`. The receipt format and chaining construction are unchanged, so existing receipts still verify (#2640).
- The `agy` adapter now passes explicitly configured models through the CLI's `--model` flag instead of silently using the backend default (#2812).
- AI-BOM adapter entries are no longer collapsed by binary: `AdapterEntry` records `binary`, but the dedupe key was `(name, version, sha256)` only, so two adapters sharing a name/version/hash but resolved from different binaries merged into one entry, and *which* binary survived depended on the order the snapshot listed them in. The emitted BOM therefore stopped being a pure function of the run, and named a binary the run may not have used - a false statement in a document meant for compliance review, and one that reached both the CycloneDX (`bernstein:binary` property) and SPDX (`bernstein:binary` annotation) encodings. `binary` is now part of the adapter identity, so the entries stay distinct and the output is canonical under any input permutation. The ordering key used by `verify_bom` is extended to match, making adapter ordering total so a swap of two otherwise-equal adapter entries is detected as tampering rather than tying.
- Role prompt templates now actually render: the orchestrator passed the templates *root* (`get_templates_dir(workdir)`) to `AgentSpawner`, whose internal contract (`render_role_prompt`, `_render_fallback`, per-role `config.yaml` lookup, available-role listing) expects the `templates/roles/` directory - so every role template lookup raised `FileNotFoundError` and silently degraded to the generic `"You are a {role} specialist."` fallback whenever no Agency catalog persona matched. Present since v1.0.0; masked in most runs by the catalog override. The call site now appends `/ "roles"`, and the previously-silent `logger.debug` fallback in `_render_prompt` is a `logger.warning` that names the failing `templates_dir`.
- The manager role always uses its own role template even when an Agency catalog persona fuzzy-matches (e.g. "Product Manager"): the manager template carries the task-server task-creation instructions that no catalog persona defines, so the persona override silently broke goal decomposition - the manager ran to the stall timeout without ever creating child tasks.
- `bernstein run --model X` is now honored for manager-created child tasks, not just the seed task. The orchestrator subprocess gains a `--model` arg (env fallback `BERNSTEIN_MODEL`) threaded from run bootstrap, `AgentSpawner` accepts `default_model`, and `_coerce_model_for_non_claude_adapter` - previously a universal no-op because no adapter defines `default_model` - uses it to replace internal Claude tier names (`opus`/`sonnet`/`haiku`) emitted by the heuristic/bandit selectors and retry escalation, which non-Claude endpoints reject (e.g. MiniMax HTTP 400 `unknown model 'opus'`). Deliberate pins are preserved: `bernstein ab-test` task creation stamps `metadata.pinned_model = true`, which the coercion guard respects, and any non-tier model name passes through untouched. Watchdog-triggered spawner restarts now re-thread both `--adapter` and `--model` (previously both were dropped on restart).
- `STALL_THRESHOLD_S` raised from 90s to 170s with an accurate comment naming the adjacent 180s idle-log agent reaper (`AGENT.idle_log_age_threshold_s`): slower non-Claude managers routinely need >90s just to investigate the codebase before creating their first task.
- The smart command/tool auto-approve classifier (`src/bernstein/core/security/auto_approve.py`) is now wired into the live tool-call approval path (`bernstein.core.approval.gate.await_tool_call`); previously it was unit-tested but never invoked at runtime, so its deny-list and evasion defenses gated nothing in a live run. Precedence is deny-wins and the posture is fail-closed: a deny-listed command (`rm -rf`, `git push --force`, `DROP TABLE`, `curl ... | bash`, control-plane/credential writes, and the rest of the list) is rejected by the production path regardless of interactive mode, and every decision the gate acts on is appended to the HMAC-chained audit log under `.sdd/audit/` as an `auto_approve_decision` event carrying the matched pattern - so an auditor can replay the chain and prove which calls were rejected or auto-approved and why. A safe verdict only short-circuits the operator queue when `approvals.smart_auto_approve: true` is set in `bernstein.yaml` (default `false`); an ambiguous verdict, or any classifier error, always falls through to human review and never auto-approves. `NotebookEdit` is removed from the classifier's safe-tools allow list so it falls through to ASK like `Edit`/`Write`, matching the edit-tool classification used elsewhere in the codebase (`observability/traces.py`). A regression test asserts the gate actually invokes the classifier, so the wiring cannot silently rot back into dead code (#1850).
- Sandbox relaxation no longer drops the `scope_enforcement` guardrail for backends that expose the whole repository. The relaxation (`relax_sandboxed`) assumed container isolation makes the task write-scope check redundant, but the Docker backend bind-mounts the entire repo read-only at `/host-repo` so `git checkout` keeps full history, leaving every file reachable. Relaxing `scope_enforcement` there removed the write-scope boundary in exactly the mode where the filesystem still exposes the full repo, so an out-of-scope write was auto-approved to ALLOW. Relaxation of `scope_enforcement` is now gated on the active backend declaring a task-scoped mount (new `SandboxCapability.SCOPED_MOUNT`, resolved from `BERNSTEIN_SANDBOX_RUNTIME`); a whole-repo mount keeps the boundary enforced (ASK), while a backend that genuinely scopes its mount can still opt in. `file_permissions` relaxation and the non-sandboxed path are unchanged. Reported by Dmitriy Filatov (Malder).
- Intent capsule verification now derives every authoritative value from signed or Merkle-chained state instead of from caller-supplied or unsigned input (#2649). `verify_intent_conformance` took the run to verify from the unsigned on-disk capsule record, so repointing that record's `run_id` at any clean run laundered a drifted run into a clean verdict; the run is now read from the signed `intent.capsule` audit entry, a capsule record naming a different run fails as tampering, and the journal must carry exactly one `intent.capsule_bound` anchor matching the task and capsule hash before conformance is evaluated. `evaluate_conformance` recorded `file_scope_globs`, `permitted_adapters`, and `expiry_ts` without enforcing any of them and treated `allow_unclassified` as a no-op, so a capsule's declared scope constrained nothing beyond its action-class allow-list; all four are now enforced as divergences (`file_scope_violation`, `adapter_not_permitted`, `capsule_expired`, `unclassified_event`), with segment-wise glob matching so `src/*.py` no longer admits `src/nested/deep.py`. `classify_journal_event` resolved a worker-stamped `action_class` ahead of the reviewed tool map, letting a drifting worker relabel its own actions (a `Bash` call stamped `git.commit` classified as a commit); the reviewed map now wins and the stamped label is the fallback for unrecognised tools only. `assemble_intent_drift_escalation` signed whatever capsule and verdict its caller passed, so a caller could mint a signed, spine-anchored receipt attesting drift against a fully conformant run by supplying a fabricated capsule plus a self-consistent verdict; it now resolves the capsule through the same chained authority the verifier uses (it must match the `intent.capsule` entry, the run must be the signed one, and the journal must carry the matching capsule-bound anchor), then recomputes the verdict and signs only that. Capsule expiry is enforced against HMAC-covered audit-chain timestamps rather than the journal's `ts` field, which is excluded from the payload hash and so could be edited in place to erase or manufacture a divergence in a signed verdict. Tool names are normalised before the reviewed map is consulted, so a trailing space no longer lets a worker-stamped label win; common shell aliases are mapped. Every action class an event claims is now checked rather than only the most authoritative one: `tool` and `action_class` are both worker-written, so preferring either alone moved which field was authoritative instead of removing worker control, and a `Read` call honestly stamping `shell.exec` was being silenced by the reviewed map. Only events that claim to be actions can count as `unclassified_event`, so `allow_unclassified: false` no longer flags ordinary structural journal rows. File-scope checking fails closed: a mutating action that records no path while a scope is declared is a `path_unrecorded` divergence. A capsule-governed run now has three distinct verification states. `seal_capsules_bound_to_run`, called by the orchestrator at run completion, commits the journal's head hash and event count to the chain as a new `intent.journal_seal` event; the journal's Merkle chain recomputes from genesis, so every prefix of a valid journal verified cleanly on its own and a worker could delete the trailing rows that convicted it. A **sealed** run is fully attested (truncation and same-length rewrites both detected, the latter by the head hash alone); an **unsealed** run still has its conformance computed and any drift reported, but its completeness is explicitly not attested (exit 4), because withholding drift until a seal exists would let a worker suppress its own drift by never finishing; a **mismatched** seal is tampering. Drift escalation works on in-flight runs and records the seal state it was cut under. Sealing is idempotent: a retry returns the existing entry and writes nothing, since the process writing an attestation can die between the write and the acknowledgement and a duplicate could never be withdrawn from an append-only chain. Capsule expiry is checked against capsule-lifecycle chain entries only (approval, seal, drift): approval entries alone could only ever flag a capsule minted already-expired, while scanning every entry carrying the same `task_id` matched 27 unrelated event types and let one ordinary later entry condemn an honest run permanently. `permitted_adapters` and `file_scope_globs` fail closed on absent input (`adapter_unrecorded`, `path_unrecorded`), since a constraint that applies only when the worker volunteers the field being checked is not a constraint. Absolute paths no longer satisfy workspace-relative globs. `IntentCapsule` normalises its field types on construction, matching the coercion `from_dict` already applied on read: without it a loosely-typed value (a float `expiry_ts`, as an upstream `time.time() + ttl` produces) canonicalised one way in memory and another after a round trip, so verification rejected an honest capsule as tampered. Read-only `bernstein intent verify` minted and wrote audit HMAC key material when none existed, producing a key that cannot authenticate the existing chain and reporting the resulting HMAC failures as tampering; it now loads the key read-only via `load_audit_key` and exits `3` with an explicit missing-key error.
- The spawned-agent prompt path did not enforce the `source_adapter` provenance filter that `SQLiteMemoryStore.query()` and `CrossTaskKB.subscribe()` already supported: `_load_persistent_memory()` read every matching row via `get_relevant()`, which had no adapter filter at all, and injected the content into the prompt verbatim regardless of which adapter wrote it. A row written under one adapter's provenance (or a foreign one) could therefore steer a different adapter's spawned agent. `get_relevant()` now accepts the same `read_only_from_adapters` allow-list as `query()`, and `_load_persistent_memory()` enforces a `MemoryTrustPolicy` (`bernstein.core.memory.trust_policy`) by default: untagged rows (today's operator/CLI writes, and pre-migration data) stay trusted, but a row tagged with an explicit `source_adapter` is only replayed if that adapter is on the policy's allow-list. Configurable via `BERNSTEIN_MEMORY_TRUST_POLICY` / `BERNSTEIN_MEMORY_TRUST_ADAPTERS`; see `docs/operations/memory.md`. Reported by Dmitriy Filatov (Malder).
